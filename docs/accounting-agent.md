# Dream Poker Accounting

Accounting은 기존 게임·바이인·F&B 입력을 유지하면서, 캐셔가 Viber로 보낸 일일 정산을 근거로 기간별 정산 초안을 만듭니다. 보고서는 요청한 정산방에 전달하며 김지영 대표에게 보내거나 공유 권한을 추가하는 기능은 없습니다.

## 정산방에서 사용

| 요청 | 처리 |
| --- | --- |
| 게임 사진 또는 기존 바이인/F&B 요청 | 기존 검증·중복 방지·수식 보호를 거쳐 입력표에 반영 |
| 사진에 `바이버 정산` 또는 `캐셔 정산` | 명시된 날짜와 일일 총액을 대사 근거로 저장 |
| `/viber 2026-10-12 …` 또는 `/cashier 2026-10-12 …` | 텍스트 형태의 캐셔 일일 총액을 저장 |
| `대사자료 제외 12` | 정산방 관리자만 해당 자료를 대사 대상에서 제외 |
| `주간 정산 2026-10-12 ~ 2026-10-18 급여 0` | 기간별 대사, 저장된 초안 ID, CSV 파일을 정산방에 제공 |
| `지난주 정산 급여 0` | 베트남 현지 날짜 기준 지난 월요일~일요일 초안 |
| `주간 정산 2026-10-12 ~ 2026-10-18 급여 0 시트 초안 작성` | 같은 초안을 기존 워크북의 새 Google Sheets 탭에도 작성 |
| `시트 초안 작성 <초안 ID>` | 이미 저장된 보고서로 Google Sheets 초안 탭 작성 또는 검증 |

`급여 0`은 해당 기간의 베트남 직원 급여 선지출이 없다는 명시적 확인입니다. 금액이 있으면 실제 정수 VND 금액을 넣습니다. 금액을 생략하면 기존 `주간 정산` 탭에서 선택된 기간이 정확히 일치하고 B13에 숫자가 있을 때만 사용합니다. 그 밖의 경우에는 `확인 필요`로 남깁니다.

기간은 시작일·종료일을 포함해 최대 31일입니다. `이번주 정산`과 `지난주 정산`은 베트남 월요일~일요일을 사용합니다. 일반 `주간 정산`은 기간을 먼저 확인합니다. 자동 마감 일정은 등록하지 않습니다.

## 대사와 계산 기준

보고서는 `일일 입력`의 A:O 전체와 `F&B 입력`의 A:D 전체를 읽습니다. 기존 입력 화면의 행 수 제한을 보고서 합계에 적용하지 않습니다. 현재 시트의 계산 결과를 사용하고, 다음 기존 주간 정산 수식을 유지합니다.

- TOTAL EXPENSE = F&B + MONGOL + JAPAN + CHINA (AK) + HOUSE + KOREA2 + 베트남 직원 급여 선지출
- NET PROFIT / LOSS = TOTAL RAKE BACK − TOTAL EXPENSE
- PARTNER 1과 PARTNER 2 = `ROUND(NET / 2, -3)`
- PARTNER 3 = 앞의 두 배분액을 뺀 잔액

파트너 계산은 기존 B18:B20 수식과 일치하는지 확인합니다. 이 수식은 현재 파일에서 확인된 계산 방식이며, 별도의 지분율 또는 송금 승인을 의미하지 않습니다. 수식 오류·날짜 누락·중복 게임 행이 발견되면 관련 문제를 표시하고 최종 순손익/지급액을 확정하지 않습니다.

Viber 캐셔 메시지는 캐셔 자료를 전달받은 하나의 출처입니다. 동일 총액을 여러 번 보내도 합산하지 않습니다. 같은 날짜·항목의 서로 다른 총액은 충돌로 표시하고 임의로 최신 값을 선택하지 않습니다. 원본에 없는 금액은 0으로 채우지 않습니다. 잘못된 자료를 관리자 명령으로 제외한 뒤 새 정산 요청을 하면 다시 계산합니다.

기본 필수 대사 항목은 `rakeBack,fnb,mongol,japan,china,house,korea2`입니다. 원본이 실제로 포함하는 항목은 운영자가 확인해야 합니다. F&B가 캐셔 보고서에 포함되지 않는 등 확인된 운영 규칙이 있으면 `ACCOUNTING_RECONCILIATION_METRICS`를 쉼표 목록으로 설정할 수 있습니다. 필수 대사에서 F&B를 제외해도 F&B 지출은 입력표 검증과 순손익 계산에 계속 포함됩니다. BUY IN과 RAKE는 기본 참고 항목이며, 자료가 있으면 비교하고 불일치를 표시합니다.

빈 날짜를 휴무로 추정하지 않습니다. 선택 기간 내 활동이 없는 날도 필수 항목에 대한 캐셔의 명시적인 0원 자료가 있어야 대사가 완료됩니다. 확인되지 않은 날은 `원본 없음`으로 남습니다. 필수 항목 목록과 각 항목의 필수/참고 구분은 CSV와 시트 초안에 표시합니다.

초안 상태는 `needs_review` 또는 `ready_for_review`입니다. 두 상태 모두 검토용이며, 외부 전송은 하지 않습니다. 근거 자료는 기간·출처·Telegram 메시지 참조와 함께 보존합니다.

## Google Sheets 초안 탭

기본 정산 요청은 저장된 보고서와 CSV를 만듭니다. 명시적인 `시트 초안 작성` 요청 또는 관리자 API의 `createSheetDraft: true`에만 새 탭을 만듭니다.

탭 이름에 보고서의 전체 UUID가 들어갑니다. 탭 생성과 소유 표시를 한 번의 원자적 요청으로 실행한 다음 보고서 값을 RAW로 쓰고 다시 읽어 확인합니다. 같은 보고서 요청을 재시도하면 기존 탭을 확인해 재사용합니다. ID·이름이 다른 탭과 겹치거나 사람이 기존 초안을 고쳤으면 덮어쓰지 않습니다. 네트워크 오류 후에도 같은 초안 ID로 결과를 확인할 수 있습니다.

기존 입력·수식·주간 정산 탭은 이 기능으로 수정하지 않습니다. Google 공유 대상도 변경하지 않습니다. 정산 초안은 저장 당시의 스냅샷입니다. 새로운 근거 또는 입력 변경을 반영하려면 새 주간 정산 요청을 합니다.

## 전용 Accounting 봇으로 전환

`ACCOUNTING_BOT_MODE` 기본값은 `legacy`입니다. 새 토큰을 환경변수에 추가하는 것만으로 현재 봇이 전환되지는 않습니다.

| 환경변수 | 용도 |
| --- | --- |
| `ACCOUNTING_BOT_MODE` | `legacy` 또는 `dedicated` |
| `ACCOUNTING_TELEGRAM_BOT_TOKEN` | 전용 Accounting 봇 토큰 |
| `ACCOUNTING_TELEGRAM_WEBHOOK_SECRET` | 전용 웹훅 인증값 |
| `ACCOUNTING_TELEGRAM_CHAT_ID` | 명시적으로 지정한 정산방 ID, 다른 방으로 대체하지 않음 |
| `ACCOUNTING_TELEGRAM_BOT_USERNAME` | 선택적인 봇 사용자명 검증 |
| `ACCOUNTING_ACTIVATED_AT` | 타임존을 포함한 ISO 전환 시각, dedicated 모드 필수 |
| `ACCOUNTING_ENABLED` | Accounting 처리 활성화 |
| `ACCOUNTING_RECONCILIATION_METRICS` | 확인된 캐셔 보고서의 필수 대사 항목 목록 |
| `ACCOUNTING_AI_MODEL` | Accounting 자료 추출 모델, 생략 시 기존 `AI_GATEWAY_MODEL` 사용 |

기존 Supabase 서비스 키, Google 서비스 계정, AI Gateway 인증 설정을 같은 백엔드에서 사용합니다. 토큰 값이나 비밀 인증값을 커밋하지 않습니다.

1. 기존 회계 테이블과 잠금 RPC가 있는 프로젝트에 `20261021103430_accounting_bot_identity_and_weekly_drafts.sql`을 적용합니다. 이 마이그레이션은 기존 `update_id` 기본키와 배포 중인 upsert를 유지합니다.
2. 전용 Accounting 봇을 정산방에 추가하고 필요한 메시지 읽기 권한을 확인합니다.
3. 전용 토큰·인증값·정산방 ID를 설정합니다. Reservations 또는 Exchange와 같은 봇 ID를 재사용하면 런타임에서 거부합니다.
4. 전환 시각을 정하고 `ACCOUNTING_ACTIVATED_AT`에 설정한 뒤 `ACCOUNTING_BOT_MODE=dedicated`로 배포합니다. 이전 시각의 Telegram 대기 메시지는 입력하지 않습니다.
5. 각 봇의 웹훅을 역할별 경로로 연결합니다. Accounting은 `/api/accounting/webhook`, Reservations는 전용 `/api/reservations/webhook`을 사용합니다. 기존 Reservations 대기열을 일괄 삭제하지 않습니다.
6. 기존 업무 규칙을 전환 직전에 복사했는지 확인합니다. 마이그레이션 이후 legacy 봇에 새로 가르친 규칙은 자동으로 다시 복사되지 않습니다.
7. 역할별 연결 상태와 합성 데이터 테스트 결과를 확인한 뒤 실제 정산방 흐름을 검증합니다.

legacy 모드에서는 기존 봇의 단일 웹훅이 예약방 메시지를 Reservations 처리기로 위임합니다. 이 위임은 Accounting이 일시 중지되어도 예약이 활성화되어 있으면 동작합니다. dedicated Accounting 인증값으로 예약 처리기를 호출할 수 없습니다.

새 이벤트 키는 `(bot_id, update_id)`입니다. 정산방의 기존 메시지와 이미 처리한 사진을 전환 전 작업까지 확인하여 같은 자료를 다시 입력하지 않습니다. 기존 워크북 잠금·작성 전 비교·RAW 입력·작성 후 확인 흐름도 유지합니다.

## 관리자 API와 검증

`POST /api/accounting/report`는 관리자 로그인 또는 `ACCOUNTING_OPS_SECRET` 인증이 필요합니다. `startDate`, `endDate`, 선택적인 `salaryAdvanceVnd`·`evidence`를 받아 초안을 저장합니다. `createSheetDraft: true`를 추가하면 새 시트 탭도 작성합니다. 이미 저장된 보고서는 `id`와 해당 플래그를 전달해 시트로 만들 수 있습니다. `send`, `recipient`, `destination` 요청은 거부합니다.

`GET /api/accounting/report?id=<id>`는 현재 정산방의 보고서만 반환합니다. `format=csv`를 붙이면 CSV를 받습니다. 새로운 테이블은 RLS를 사용하고 익명/일반 인증 클라이언트에 읽기 권한을 부여하지 않습니다.

로컬 테스트는 기존 게임/F&B 계산, 역할별 인증과 웹훅 위임, 전환 전 메시지 무시, 중복 방지, 합계·대사·반올림, 누락·충돌·휴무 처리, 초안 탭 충돌·수정 방지·오류 복구를 확인합니다. PGlite에서 additive SQL 및 권한도 확인합니다. 로컬 검증은 실제 배포·운영 DB 마이그레이션·Telegram 왕복 검증을 대신하지 않습니다.
