# 세 에이전트 운영 적용

이 문서는 구현된 기능을 실제 운영으로 전환하는 순서입니다. 저장소에 SQL이 존재하거나 테스트가 통과한 것만으로 운영 DB에 적용됐다는 의미는 아닙니다.

## 1. 대상과 설정 확인

같은 운영 Supabase 프로젝트, Google Sheets 워크북, Vercel 프로젝트를 유지합니다. 기존 예약 계정은 `Dream Buy-in Desk`이며 사용자명을 변경하지 않습니다. Accounting과 Exchange는 각각 별도 계정을 사용합니다.

예약방, 비공개 정산방, 환전방은 각각 정확한 숫자 chat ID를 설정합니다. **Accounting 전용 방을 기존 STAFF 방으로 자동 대체하지 않습니다.** 정산방 구성원이 요청한 대상과 일치하는지 먼저 확인합니다. 봇은 일반 메시지를 받을 수 있어야 하지만 불필요한 관리자 권한은 요구하지 않습니다.

`.env.example`에 설정 이름을 정리했습니다. 각 역할에 서로 다른 webhook secret을 생성하고 비밀 환경변수에 저장합니다. 봇 토큰·서비스 키·비공개 방 ID는 PR 본문이나 공개 저장소에 기록하지 않습니다. 계정 이름만으로 관리자 권한을 추정하지 않으며 숫자 Telegram ID allowlist를 사용합니다.

## 2. 데이터베이스와 배포

운영 전환 직전에 다음 SQL을 검토하고 해당 프로젝트에 적용합니다.

1. `supabase/reservation_agent.sql`
2. `supabase/exchange_agent.sql`
3. `supabase/migrations/20261021103430_accounting_bot_identity_and_weekly_drafts.sql`

예약 SQL은 기존 테이블에 좌석 검증 trigger와 임시 확보 연결을 추가합니다. 기존 게임·손님을 일괄 수정하지 않으며, 이미 열린 빈 게임은 직원 화면에서 초기 hold를 지정할 수 있습니다. 과도한 hold가 있는 상태에서 신규 정원을 줄이려면 먼저 불필요한 hold를 해제합니다.

Accounting migration은 이전 규칙을 신규 역할 테이블로 복사합니다. **마이그레이션 이후 legacy 봇에 추가된 규칙은 자동 동기화하지 않으므로 전환 직전에 복사 상태를 확인해야 합니다.** 기존 job 기본키와 legacy 쓰기 경로는 보존됩니다.

검증된 브랜치를 배포하되 활성화 설정은 명시적으로 제어합니다. 초기에는 `ACCOUNTING_BOT_MODE=legacy`를 유지할 수 있습니다. 새 봇 토큰을 저장하는 것만으로 회계 처리가 바뀌지 않습니다. Preview 배포에서는 운영 웹훅을 변경할 수 없습니다.

## 3. 전용 계정으로 전환

1. 담당 관리자 ID, 정확한 업무방, 전용 토큰/인증값을 설정합니다.
2. Accounting/Exchange 각각의 전환 시각을 타임존 포함 ISO 형식으로 정합니다. 전환 이전 대기 메시지는 자동 입력하지 않습니다.
3. `ACCOUNTING_BOT_MODE=dedicated`와 역할별 활성화 값을 적용하여 운영 배포합니다.
4. 관리자로 `/agents`에 로그인하고 실제 계정과 방을 확인합니다. Accounting, Reservations, Exchange 웹훅을 각각 연결합니다. 연결된 봇도 인증값 갱신 시 다시 연결할 수 있습니다.
5. 기존 예약 봇의 webhook을 `/api/accounting/webhook`에서 `/api/reservations/webhook`으로 이동합니다. pending queue는 일괄 삭제하지 않습니다.
6. 기초 시제를 관리자가 입력하고 미리보기를 확인한 뒤 확정합니다. 과거 메시지 잔액을 자동으로 복사하지 않습니다.
7. 실제 화면과 `/games`, `시제` 등 읽기 요청으로 전달 결과를 확인합니다. 운영 기록 검증은 이미 발생한 승인된 실제 거래로 수행합니다. 가짜 금융 거래를 운영 원장에 넣지 않습니다.

Accounting은 전환 중에도 기존 워크북 mutex를 공유하고 이전 봇이 처리한 메시지·사진을 확인합니다. 이전 처리 상태가 불확실하면 재입력 대신 검토 상태로 남깁니다. 새 계정의 동작을 확인하기 전에는 기존 계정을 업무방에서 제거하지 않습니다.

## 중지와 복구

문제가 생기면 해당 역할의 활성화 값부터 끕니다. 새 원장이나 감사 데이터를 삭제하지 않습니다. 실제 원장 반영 여부를 확인하고 동일 거래의 재입력을 피합니다. Accounting을 legacy로 되돌릴 때는 전환 후 작업 상태를 대조하고 웹훅 경로·인증값을 함께 복구해야 합니다. 토큰을 바꾸는 것만으로 복구됐다고 판단하지 않습니다.

보고서는 요청한 정산방에서 검토하는 초안입니다. 대표에게 외부 발송하거나 공유 대상을 늘리는 단계는 별도의 사용자 요청이 있을 때 진행합니다.
