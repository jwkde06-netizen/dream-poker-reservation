# Dream Poker 예약 운영 전환

## 운영 원칙

- 손님: `/`, 한국인 데스크: `/desk`, 캐셔: `/cashier`.
- 데스크가 카카오톡으로 받은 이름·게임·도착 시간·인원·메모를 직접 입력한다. 카카오톡 자동 수신은 미구현이다.
- 신청은 `pending`으로 시작한다. 데스크 권한으로 확정할 수 없다. 캐셔, 관리자 또는 기존 공용 직원 권한이 승인한다.
- 변경·취소 요청은 같은 예약에 저장하며, 승인 전에는 기존 내용과 좌석을 유지한다. 거절 또는 조정 시 답변을 필수로 받는다.
- 승인·취소·방문 확인은 정산 거래가 아니다. **BUY IN과 금액은 기존 영수증 스캔 절차로만 기록한다.**
- `예약 현황` 탭은 별도 자동 출력이다. `일일 입력`과 금액 계산식은 수정하지 않는다. 이름·날짜·테이블·게임이 일치하는 정산 기록을 참고 정보로 보여주며, 일치하지 않아도 자동 노쇼 처리하지 않는다. 여러 명 예약은 대표자 기록만 대조할 수 있다.
- 상태와 주요 항목은 한국어·베트남어로 함께 표시한다. 자유 입력 메모·답변은 자동 번역하지 않으며 간단한 영어 사용도 가능하다.

## 구현과 검증 범위

공통 PostgreSQL 처리 함수가 웹과 Telegram을 함께 처리한다. 요청 ID로 응답 유실 후 재시도를 재사용하고, 예약 버전 비교와 좌석 잠금으로 변경 충돌을 거부한다. 정원은 예약 건수가 아닌 인원 합계로 검사한다. 이름의 대소문자·연속 공백과 같은 계정의 중복 신청을 검사한다. 처리자와 이전/이후 내용은 이력에 남긴다.

화면은 Supabase Realtime 구독과 2초 간격 확인을 사용한다. 마지막 갱신 시각과 연결 실패를 표시한다. Telegram은 기존 전송 큐와 두 개 버튼을 재사용한다. 앱을 닫았을 때의 푸시 알림은 미구현이다.

시트 출력은 별도 잠금·재시도 큐를 사용한다. 고정된 기존 워크북의 `예약 현황!A:R`만 RAW 값으로 쓰고 다시 읽어 검증한 뒤 성공 처리한다. 영수증 대조는 `일일 입력!A:I`를 읽기만 한다. 즉시 반영 시도 후 분당 재시도하며, 영수증 변경 반영을 위해 5분마다 다시 확인한다. Google Sheets는 외부 서비스이므로 DB 변경과 한 트랜잭션은 아니며 실패·대기 상태가 화면에 표시된다.

### 통과한 검증

- TypeScript 검사와 기존 영수증·정산 회귀 테스트.
- 실제 변경 SQL을 분리된 PostgreSQL(PGlite 0.5.11)에 적용 후 신청 → 승인, 변경 승인, 취소 승인, 거절 사유, 권한 거부, 재시도, 오래된 버전 거부, 인원 정원, 정원 축소 방어, 처리 이력 검증.
- Telegram 기존 메시지 컨텍스트 검사, 같은 예약 행 승인·취소, 오래된 버튼 재사용 거부, 시트 작업 잠금·실패·재시도 완료 검증. 외부 전송은 로컬 테스트에서 차단한 상태다.
- 실제 운영 React 화면을 두 브라우저 탭에서 실행하여 요청 수신 → 승인 → 데스크 자동 갱신 및 2명 → 3명 변경 승인 확인. 테스트 서버는 같은 SQL을 실행하지만 Supabase Auth·Realtime·외부 메시지 전송은 대신하지 않는다.
- 시트 쓰기 대상 제한, RAW 입력, 읽기 검증 실패 시 미완료 처리, 영수증 기록이 있어도 방문·금액을 자동 생성하지 않는 검사.

### 운영 검증 결과 (2026-10-24)

- 소유자 승인 후 PR #46을 병합하고 기존 프로덕션 도메인에 배포했다. 운영 DB 단계별 적용과 rollback 검증을 통과했다.
- 실제 로그인된 `/desk?test=1`와 `/cashier?test=1` 두 Chrome 탭에서 TEST LIVE MIN JUN 요청 → 2명 승인 → 3명 변경 요청/승인 → 취소 요청/승인을 확인했다. 새로고침 없이 양쪽 상태가 바뀌었고 승인 전 좌석이 유지됐다.
- TEST LIVE HANA 거절 사유가 데스크에 자동 표시됐다. 실제 운영 서버/DB/Auth를 사용했으며 외부 전송만 차단한 보호된 검증 기록이다. 물리적으로 다른 휴대폰 두 대에서의 현장 검사는 대신하지 않는다.
- 실제 Supabase에 두 동시 승인 트랜잭션을 보냈다. 정원 1명의 검증 게임에서 한 건만 확정되고 다른 건은 정원 부족으로 거부됐다. 검증 예약은 종료 처리했으며 이력은 남겼다.
- 기존 워크북의 `예약 현황`(gid=463274032)에 운영 예약 14건이 서비스 계정으로 출력됐고 재조회 검증이 성공했다. 검증 예약은 제외됐으며 원본 정산 수식·값 비교도 동일했다.
- 검증 예약으로 생성된 Telegram 작업 0건, 시트 변경 요청 0건. 신규 운영 예약이나 정산 거래를 만들지 않았다.
- 새 Telegram 포맷과 버튼은 배포됐고 공통 DB 처리·오래된 버튼·잘못된 방 검사는 통과했다. 실제 방으로 새 메시지를 보내는 검사는 고객 알림 방해를 피하기 위해 수행하지 않았다.
- 화면 내 자동 갱신은 확인했다. 카톡 자동 수신 및 앱을 닫았을 때 푸시는 미구현이다.

## 운영 반영 순서

2026-10-24 소유자가 운영 반영과 최종 검증을 명시적으로 승인했다. 아래 절차는 적용 완료한 변경의 기록이다. 자동 승인 검토가 요구했던 단계별 적용과 검증을 수행했다.

1. 최신 main과 현재 운영 배포를 다시 확인하고, 예약 관련 함수 정의와 현재 테이블 구조를 보관한다. 기존 정산 변경을 보존한다.
2. `20261024092735_reservation_operations.sql`: 필요한 데이터 항목과 내부 요청 영수증 테이블만 추가한다. 운영 행·금액을 삭제하거나 생성하지 않는다.
3. `20261024094526_reservation_operations_transitions.sql`: 공통 승인 처리와 기존 웹·Telegram 호환 함수를 적용한다. 데스크는 요청만 가능하도록 서버에서 검사한다.
4. `20261024094527_reservation_sheet_delivery.sql`: 검증 예약의 외부 전송 차단, 시트 큐, 실시간 구독을 적용한다. 시트 전송은 `enabled=false`로 시작한다.
5. `20261024100342_reservation_test_queue_isolation.sql`로 기존 운영 대기열과 검증 대기열의 단일 큐 제약을 분리한다. `20261024101021_reservation_request_actor_label.sql`은 표시명이 빈 기존 직원의 사용자명으로 이력을 남긴다. `tests/reservation-operations.sql`을 트랜잭션 안에서 실행하고 rollback을 확인한다. **`tests/reservation-delivery-postgres.sql`은 로컬 전용이며 운영에서 실행하지 않는다.**
6. 예약 관련 보안 권고와 권한을 다시 검사하고, 검증된 앱 빌드를 기존 Vercel 프로젝트에 배포한다.
7. 기존 워크북 `1QJUPswetSgSFAlKkDXdY_WMmM6LCp6nXs9EvmuQF22I`에 `예약 현황` 탭을 추가한다. 정확한 헤더·고정 행·열 폭을 설정하고 원본 정산 수식이 유지되는지 확인한다. 테스트 이름을 시트에 보내지 않는다.
8. 시트 연결의 헤더/접근 확인 후 내부 `sheet_sync.enabled`를 켠다. 첫 읽기 검증이 성공하고 실패 상태가 비어 있는지 확인한다.
9. 관리자 로그인에서 `/desk?test=1`의 검증 게임을 준비하고 `/cashier?test=1`에서 같은 예약을 처리한다. 이 화면은 실제 역할과 같은 운영 처리 함수를 사용하지만 검증 게임·예약은 손님과 외부 알림/정산 출력에서 제외된다. 양쪽 화면에서 실제 동기화를 확인한 후 운영 링크를 전달한다.

새로운 유료 서비스나 새로운 외부 인증 연결은 필요하지 않다. 현재 활성 계정은 관리자와 공용 직원이며 전용 desk/cashier 계정은 별도 배정이 필요하다. 기존 계정 관리 화면으로 관리자가 담당자 계정을 설정한다. 비밀번호를 코드나 문서에 기록하지 않는다. 개인별 처리자 추적에는 개인별 계정이 필요하다.

현재 기본 Next 5M 대기열에는 이전 테스트/예약이 남아 있으므로 임의로 고객 예약을 취소하거나 좌석을 비우지 않는다. 캐셔가 실제 운영할 게임·정원·시작 시간을 등록하고 기존 요청을 확인해 배정해야 한다.

## 오류 시 복구

- 시트 오류: `sheet_sync.enabled=false`로 출력을 중지한다. 예약과 영수증 입력에는 영향을 주지 않는다. 헤더·권한을 복구한 뒤 재활성화하면 같은 전용 범위를 다시 읽고 쓴다.
- 앱 오류: 직전 배포로 되돌릴 수 있지만 이전 화면은 인원·변경 요청 상세를 이해하지 못한다. 이 경우 신규 승인/변경을 잠시 중단하고 수정 배포를 우선한다. 그룹 예약이 존재하는 상태에서 이전 1명 기준 승인 함수를 복원하지 않는다.
- 데이터 변경은 추가형이며 새 열·이력을 삭제하는 다운그레이드를 하지 않는다. 문제가 있는 상태 변경은 이력을 보고 승인된 직원 작업으로 바로잡는다.
